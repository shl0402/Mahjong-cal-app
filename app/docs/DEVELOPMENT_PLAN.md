# Mahjong camera app development proposal

Prepared for Samuel on 2 October 2026. **Historical proposal:** development has since started and version 0.3.0+3 is being validated for local testing. The current implementation uses continuous native camera scanning, ONNX Runtime inference, iOS 16+/Android 7+, local settings/history, and two executable rule packs. It is not the completed broad catalogue described below. Current status is in [CONTINUE_HERE.md](CONTINUE_HERE.md), [BUILD_VALIDATION.md](BUILD_VALIDATION.md) and [RULES_READINESS.md](RULES_READINESS.md). The proposal's still-capture/photo-import path, Core ML/LiteRT split and earlier iOS floor are superseded by the user's continuous-scanning requirement and verified implementation choices.

Build an offline-first iPhone and Android app that scans a mahjong hand, lets the player confirm uncertain tiles and game circumstances, explains the score, and calculates each player's payment under a named ruleset. Use Flutter for the shared app and scoring logic, with native camera and machine-learning components. Start real-device validation on Samuel's iPhone 13 Pro and expand to physical Android phones before claiming Android camera support is verified.

The long-term scope includes a broad catalogue of mahjong families and house preferences. Release each preset only after its rules and payments pass an explicit verification process. A long list of selectable names must never imply that unfinished rules are supported. The companion [rules research](</Users/samuel/Documents/leisure/mahjong vision/docs/RULESET_RESEARCH.md>) records sources, payment examples, differences, and remaining gaps.

**What the app should do.** The main journey is: choose a saved table preset → scan concealed tiles → add exposed groups and flowers → confirm the winning tile and circumstances → see an explained score and payment breakdown. Camera, photo import, and manual tile entry should reach the same hand editor. Users can correct a result without scanning everything again.

Offer two modes. Quick score evaluates one completed hand using the context the player supplies. Table session also remembers seats, dealer, round wind, continuations, previous payments, and event-dependent liabilities. Some rules, such as deferred debts or repeated wins, require session history. Quick score must ask for missing history or explicitly report that a final settlement cannot yet be calculated.

For an incomplete hand, say that it is not yet a winning hand. A later feature can show structural waits and conditional winning scores. Do not present a speculative future 番數 as the current score, or describe theoretically possible remaining tiles as available without the relevant visible-tile information.

**Technology and testing.** Flutter produces separate iOS and Android applications from shared Dart code. It can access cameras through plugins, and communicate with Swift or Kotlin components where needed. It does not require writing two complete interfaces. The proposed split is Flutter for screens, settings, hand validation, scoring, and local history; Core ML for iOS inference; LiteRT for Android inference, subject to an early export and performance experiment. [Flutter camera](https://pub.dev/packages/camera), [platform integration](https://docs.flutter.dev/platform-integration/platform-channels), [Core ML](https://developer.apple.com/documentation/coreml), and [LiteRT](https://developers.google.com/edge/litert).

Yes, the app can run on Samuel's iPhone through Xcode, on an iOS simulator, and on Android through Android Studio and its emulator. The shared Flutter project is normally developed using a Flutter-capable editor; Xcode remains available for signing, the native iOS project, and profiling. Physical devices are essential for validating focus, glare, camera orientation, thermal throttling, and inference latency. [iOS setup](https://docs.flutter.dev/platform-integration/ios/setup) and [Android setup](https://docs.flutter.dev/platform-integration/android/setup).

Bundle the baseline model and rules so the core app works without internet. [Flutter supported platforms](https://docs.flutter.dev/reference/supported-platforms).

A browser version can later provide convenient trial access to manual scoring and photo analysis. Treat browser camera and inference support as a separate compatibility project. The initial promise is downloadable iOS and Android apps, not every mobile operating system or every historical phone.

**What survives from the old project.** The project contains 628 JPEG images, 629 CSV rows, and 42 tile classes. The row for `582.jpg` occurs twice. The generated split contains 502 training and 126 validation images, with no filename overlap. Exact image-byte hashes show no duplicate JPEG files. This does not rule out near-duplicate photographs or shared tile-set leakage.

The CSV labels are 1–42 and match the class-name list only after subtracting one. The converter writes the original label directly into YOLO files, which require zero-based class IDs. This shifts labels and makes class 42 invalid for a 42-class model. The converter assigns every image the full-image box `0.5 0.5 1.0 1.0`; the inspected sample is a close-up of one tile. These examples may train a tile classifier, but do not supply real boxes for detecting a row of many tiles. [Converter](</Users/samuel/Documents/leisure/mahjong vision/train/formatfile.py>) and [class configuration](</Users/samuel/Documents/leisure/mahjong vision/train/data.yaml>).

The training script is a YOLOv5 entry point importing supporting modules that are absent from this workspace. No trained `.pt`, `.onnx`, `.tflite`, or `.mlmodel` files were found. There are no saved evaluation results here establishing recognition accuracy. The configuration uses zero rotation/perspective augmentation and allows horizontal flipping; these choices need revisiting for tile faces. The GPU check assumes NVIDIA CUDA and is unsuitable as a general Mac readiness check. Preserve the original files as reference and build a reproducible training pipeline separately.

**Recognition approach.** Compare two practical candidates on the same held-out phone photographs: a small detector that both locates and identifies each tile, and a tile-face detector followed by perspective correction and a small classifier. The second design may reuse the old single-tile images. Choose by measured whole-hand accuracy, speed, memory, battery use, model size, conversion reliability, and distribution terms; a newer YOLO name alone is not evidence of improvement.

Initially support a guided still capture of one player's visible hand. Provide separate capture regions for concealed tiles, exposed groups, and flowers. Follow with a short camera burst that selects sharp frames and checks whether the same tiles persist across frames. A smooth preview need not run inference on every camera frame. Keep image buffers and inference off the interface thread; discard stale queued frames instead of falling behind.

Tile identity and tile position are separate outputs. Preserve individual repeated tiles rather than suppressing adjacent identical tiles as duplicate detections. Retain the mapping from a detected tile back to its image crop. Do not use a legal-hand solver to silently change an uncertain visual prediction into whichever tile makes a winning hand. It can flag contradictions and suggest candidates for confirmation.

Confidence states should be understandable: confirmed, needs checking, unreadable, and missing. An unreadable or face-down tile remains unknown. Rescan a region or enter it manually. The model cannot recover concealed physical information, establish the order of earlier discards from one photo, or know who supplied a meld.

The initial visual vocabulary is the existing 34 ordinary tile types plus eight individually identified flowers/seasons. Expansion adds red fives, animal tiles, joker/fly tiles, regional artwork, and backs/unknowns. Recognition capability and scoring-preset availability must be tracked separately: a manual ruleset can be ready before its uncommon tiles are reliably recognised.

Training should use real labelled phone scenes, with synthetic scenes as a supplement. Collect different physical sets, printing styles, tile sizes, worn surfaces, racks, tables, lighting, shadows, reflections, camera distances, rotations, exposed meld layouts, and partial occlusion. Record consent and provenance for contributed images. Keep collection opt-in and perform ordinary scoring locally.

Split train, validation, and final test data by physical tile set and capture session before augmenting. Include unseen artwork and devices in the test set. Use real multi-tile boxes or corner labels. Audit class balance and annotation quality. Quantize only after establishing a floating-point reference; compare the exported phone model against that reference on the same examples. Ultralytics documents mobile exports, but successful export still needs device validation. [Export documentation](https://docs.ultralytics.com/modes/export).

**Proposed acceptance targets.** These are targets to review and measure, not results already achieved. Aim for at least 95% exact whole-hand recognition on a held-out, well-lit supported capture set, and at least 99.5% correctness among hands marked ready without any uncertain tiles. Report the fraction rejected or sent for review alongside that second metric so it cannot be improved by refusing almost every image. Also report failures by tile set, device, flower type, and lighting; do not hide poor cases in one average.

At 99% per-tile accuracy, an illustrative independent-error model gives only about 87% exact accuracy for 14 tiles and 84% for 17. Therefore whole-hand accuracy, correction effort, and confident mistakes matter more than a headline tile-classification percentage. On iPhone 13 Pro, target a 95th-percentile result time under 1.5 seconds after a still capture, then set an Android budget using measured devices. Test ten minutes of repeated scanning for heat and stability. If these targets fail, improve data or capture guidance before broadening the advertised scan conditions.

**Rules engine architecture.** Use a deterministic engine, independent of the vision model. Represent physical tile instances, tile identities, concealed tiles, declared melds, meld sources and order, winning tile, bonus tiles, seat and round winds, dealer state, and known/unknown win circumstances. A kong uses four physical tiles but occupies one meld slot; flowers do not count toward the ordinary hand shape. Ordinary 13-tile and 16-tile families need different hand sizes, and special wins can bypass the usual meld-and-pair structure.

Evaluate in stages: validate tiles and context → enumerate permitted hand interpretations → identify scoring patterns → apply exclusions and stacking rules → check win eligibility and minimum score → apply limits → calculate transfers between named players → update session state. The choice among interpretations follows the selected preset, normally its maximum legal score rule. Keep errors and missing facts distinct from a valid zero-bonus hand.

A rule pack needs a stable ID, version, source and section references, an original plain-language explanation, legal hand forms, pattern predicates, values, incompatibilities, context requirements, payment formulas, rounding, and event rules. Data files can express many values and options; special algorithms still require tested code. Do not promise arbitrary regional rules can all be represented by changing a few numbers.

Payment output must identify each payer, recipient, component, and reason. Track score deposits and deferred debts as explicit accounts so totals reconcile. Use integer smallest units or exact rational arithmetic, with rounding applied at the specified stage. Store the pack version and house overrides with every scored hand so updates do not silently rewrite history.

**Settings without an overwhelming interface.** Begin with a named preset and a short table summary. Allow users to duplicate it as a house preset; retain the source preset as an immutable reference. Basic settings include stake/unit size, minimum score, cap, flowers, and payment policy where the rules permit changes. Advanced sections expose pattern values, stacking, dealer rules, bonus events, liabilities, and end-of-session settlement. Each setting needs a plain-language explanation and a preview with numbers.

For example, for a deliberately simplified 120-unit hand, “each opponent pays the full amount” means 120 + 120 + 120, while “divide a fixed total equally” means 40 + 40 + 40. A dealer-weighted system may be different again. Those are example custom policies, not interchangeable official mahjong rules. Show the exact transfer preview and mark a modified preset as custom.

Do not place transient events only in settings. 自摸/出銃, the winning tile, 槓上開花, 花後補牌, 海底摸牌, 河底出牌, and 搶槓 belong to the current hand. Ask only the relevant questions for the chosen preset, and only when unresolved context can affect the result. Use “unknown” instead of quietly assuming “no.” Seat, dealer, and round context can be remembered within a session.

The score view should explain both included and excluded patterns: which tiles qualify, the points, what prevented double counting, the cap, and who pays. Let users expand the detail. Large tile targets, Traditional Chinese labels first, scalable text, colour-independent confidence indicators, and one-handed correction should be part of the interface. Simplified Chinese and English can use the same stable rule and tile IDs.

**Delivery sequence and review gates.** The complete catalogue remains the goal; these milestones make it possible to test useful builds while broad coverage develops.

Session-dependent presets may require milestone 4 before claiming complete settlement support, even if their individual-hand calculation exists earlier. In particular, a simple 港式台牌 hand calculator must not pretend to implement 拉莊 automatically without its history.

No fixed whole-project completion date is credible before the capture benchmark and rule-specification work. The main external effort is obtaining varied, correctly labelled photographs and independent rule review. Samuel does not need to be the rules expert: implementation should include source-based fixtures and review by experienced players or organisers for disputed interpretations.

**Verification and release evidence.** For each pattern, test positive, negative, boundary, and overlap examples. Include illegal tile counts, ambiguous decompositions, missing winning-tile identity, conflicting events, and invalid setting combinations. Test payment conservation, seat rotation symmetry where applicable, rounding, multiple winners, liability, carried debts, and replay/undo. Reference software can be a cross-check but must not overrule the selected written rules without explanation.

Hardware coverage should include the iPhone 13 Pro, an older supported iPhone, a low/midrange Android, and Android devices using different chipset families. Borrowed devices or a device lab can supplement ownership, but camera tests require a controlled physical scene; emulators alone cannot establish accuracy. Publish the actual tested OS and device matrix with releases rather than claiming “all phones.”

Review the chosen training framework, weights, and redistribution terms before committing to a model.
